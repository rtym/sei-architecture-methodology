System overview — Personal Finance Tracker

What it does

A mobile-web application that lets an individual record income and expense transactions, organise them into user-defined categories, see a monthly dashboard (totals, a category breakdown, recent activity, savings-goal progress), and import transactions from a bank CSV statement.

Context

Single-tenant-per-user SaaS. One external dependency at launch: a transactional email provider (account verification, security alerts). No payment processing. Runs in mobile browsers; there is no native app at launch (CON-1).

Source: diagrams/system-overview-01.puml · rendered + visually verified.

Primary functional requirements (use cases)

  • UC-1 Record a transaction
  • UC-2 View the monthly dashboard
  • UC-3 Import a bank statement (CSV)

Driving quality attribute scenarios

See ../scenarios.md for the six-part detail. The architecture is shaped mainly by:

  • SQA-1 (security / confidentiality) — cross-user access rejected and logged; 0 successful reads.
  • AQA-1 (reliability / availability) — survive a single-AZ failure, recover < 60 s, ≥ 99.5 %/mo.
  • PQA-1 (performance / time behaviour) — dashboard interactive < 1.5 s at p95, 500 concurrent users.
  • MQA-1 (maintainability / modifiability) — add a report type in ≤ 1 person-day, 0 regressions.

Allowed-dependency rule: http → security → {domain} → persistence → platform. Domain modules must not depend on one another; a cross-domain need is mediated by reporting reading via persistence. Enforced in CI by a dependency-check rule.

2.3 Element interfaces

Module APIs are internal TypeScript module boundaries. The externally visible HTTP interface is in the ADD ../add/personal-finance-tracker-Architecture.md §8.

2.4 Element behavior

Runtime collaboration for the dashboard flow is the sequence diagram in the ADD Architecture.md §6.

3. Context diagram

This view covers the api-service deployable only. The Web App (React) and the Import Worker process are outside it; the worker reuses the imports and persistence modules as a library.

4. Variability guide

  • Report types: registered in reporting via a ReportType registry entry — add a class + a registry line, no other module changes (MQA-1).
  • Storage engine: persistence isolates the query builder; swapping the SQL dialect is contained here (CON-5 currently pins PostgreSQL).
  • Import formats: imports has a StatementParser strategy; new bank formats are new strategy classes.

5. Rationale

  • The security module is the single choke point for tenant scoping so SQA-1 is enforced structurally and is auditable in one place (see rationale.md ADR-2). The alternative — per-endpoint checks in http — was rejected as too easy to miss.
  • Forbidding domain-to-domain dependencies keeps change impact local, serving MQA-1 (add a report type in ≤ 1 person-day, 0 regressions).
  • platform has no domain dependencies so it can be extracted to a shared library later without untangling business code.

4. Variability guide

  • Import processing runs in-process in the API Service in local/dev (no queue/worker) and out-of-process in production; selected by config flag IMPORTS_ASYNC.
  • Read Cache is optional: with it disabled the Dashboard Service reads straight from the DB (slower; used only in dev).

5. Rationale

  • One API Service process holds the tenant guard so SQA-1 isolation is enforced on every interactive path in a single auditable place (rationale.md ADR-2).
  • Cache-aside with a bounded TTL meets PQA-1's p95 budget while keeping the cache strictly derived, so its failure never threatens AQA-1 correctness (rationale.md ADR-1).
  • CSV import is pushed to a queue + worker so a large import cannot consume the request threads that serve interactive traffic (PQA-2).

2.3 Element interfaces

Network: only the CDN and the container platform's load balancer are public; the data tier is private-subnet only. All hops use TLS (CON-4).

2.4 Element behavior

On an AZ-a loss: the load balancer drains AZ-a API replicas, the DB standby in AZ-b is promoted, Redis fails over to its AZ-b replica; the API is stateless so no session loss.

3. Context diagram

Outside this view: the user's device/network and the email provider's infrastructure.

4. Variability guide

  • Region: single region at launch; a second region is a future option — no region-partitioning seam exists yet (ATAM risk R-6).
  • Tier sizing: instance classes and replica counts are environment config; the topology is fixed.
  • Redis split: cache and streams share one Redis at launch; they can be split onto two instances by config without code change.

5. Rationale

  • Stateless API replicas across two AZs plus a managed primary/standby database with automated failover is the cheapest topology that meets AQA-1 (recover < 60 s, ≥ 99.5 %/mo) on the low-cost managed tiers required by CON-3 and within BG-4's budget (rationale.md ADR-3).
  • Putting only the CDN and load balancer in public subnets shrinks the attack surface for SQA-1 / CON-4.
  • The measured failover time is not yet verified against the 60 s target — tracked as ATAM risk R-3; a game-day test is scheduled before launch.

2.3 Element interfaces

The Tenant Guard's contract (four agreement points — see references/interfaces.md):

  • scope: every inbound request; the guard is the actor for every domain module.
  • interaction style: synchronous, in-process middleware; fail-closed (deny on any error).
  • data representation: the authenticated user_id is taken from the verified JWT, never from a request parameter.
  • error model: unauthorised → 403, event written to the audit log, alert raised; the request never reaches a domain module.

2.4 Element behavior

Denied-access sequence: the attacker requests another user's transaction by ID → the Tenant Guard scopes the query to the attacker's own user_id → the row is not found → 403 returned → a denied-access event is written to the append-only audit log and an alert is raised within 1 minute. 0 rows of another tenant's data are ever returned.

3. Context diagram

Outside this view: the user's device, and the email provider (security alerts are delivered by the API Service via SMTP — omitted here to keep the control path clear).

4. Variability guide

  • Audit sink: the append-only store is configurable (managed log service vs. an append-only table); the tamper-evidence mechanism is a variation point tracked as ATAM risk R-2.
  • Row-level security: PostgreSQL RLS is a future alternative to the in-app Tenant Guard; the Data Access module isolates the choice.

5. Rationale

  • One Tenant Guard choke point makes SQA-1 enforceable and auditable in a single place; per-endpoint checks were rejected as too easy to omit (rationale.md ADR-2).
  • Encryption in transit and at rest satisfies CON-4 and shrinks the SOC 2 boundary for BG-2.
  • Keeping only the CDN in a public subnet minimises the attack surface for SQA-1.

Rationale — Personal Finance Tracker

Cross-cutting architecture rationale and the ADR log. Per-view rationale lives in each view packet.

ADR-1: Cache-aside read model for the dashboard

  • Status: accepted · 2026-09-06
  • Drivers addressed: PQA-1, AQA-1, MQA-1

Context. The dashboard (UC-2) must be interactive in < 1.5 s at p95 with 500 concurrent users. Computing every load from the transaction store does not meet the budget.

Decision. We will precompute per-user, per-month aggregates in a Redis cache using the cache-aside pattern with a 15-minute TTL; a transaction write invalidates the affected key.

Rationale. Meets PQA-1; keeps the cache strictly derived so its loss degrades latency but not correctness (AQA-1); aggregate logic stays in the reporting module, so new report types (MQA-1) do not require schema changes.

Alternatives considered. Materialised views (slower iteration for MQA-1); CDN edge caching (per-user private data — unsafe); no cache (fails PQA-1).

Consequences. Dashboard data can be up to 15 minutes stale on the read path (tradeoff point T-1 in the ATAM). Cache warm-up cost on cold start.

ADR-2: Single tenant-guard choke point

  • Status: accepted · 2026-09-06
  • Drivers addressed: SQA-1, CON-4, BG-2

Context. SQA-1 requires that no user can read another user's data, with every attempt logged, and BG-2 requires passing a SOC 2 audit.

Decision. All interactive requests pass through one security-module tenant guard that injects user_id scoping into every query via the persistence module; denied access is written to an append-only audit log.

Rationale. One auditable place to enforce and demonstrate isolation; per-endpoint checks were rejected as too easy to omit.

Alternatives considered. PostgreSQL row-level security (viable later; team unfamiliarity now); per-endpoint authorization (miss-a-check risk).

Consequences. The Import Worker currently bypasses the guard (ATAM risk R-1); a follow-up routes it through the same Data Access scoping. Audit-log tamper-evidence still to be decided (R-2).

ADR-3: Stateless API replicas + managed multi-AZ database

  • Status: accepted · 2026-09-06
  • Drivers addressed: AQA-1, CON-3, CON-5, BG-4

Context. AQA-1 requires surviving a single-AZ failure with recovery < 60 s at ≥ 99.5 %/mo, on low-cost managed tiers (CON-3) using PostgreSQL (CON-5) and within budget (BG-4).

Decision. Run the API as stateless replicas pinned across two AZs behind the platform load balancer; use a managed PostgreSQL primary/standby with automated failover; Redis primary/replica.

Rationale. Cheapest topology meeting the recovery target without a self-managed HA setup the one-person team cannot operate (CON-2).

Alternatives considered. Self-managed HA (operational load — CON-2); single instance (fails AQA-1); multi-region (cost — BG-4, and premature).

Consequences. Measured failover time not yet verified against 60 s (R-3); no rollback runbook yet (R-4); single-region only, no data-residency seam (R-6).
